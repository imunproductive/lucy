# Client tools

Python tools in `tools/` that answer questions about the client's code, such as those on the IDA list (`D:/Work/Coding/refs/reports/IDA-questions.md`), without a manual IDA session. Run them from the repository root.

They read what the client research produces: a dump of the running game and the decrypted game. That research and its own tools (unpacking, decrypting, dumping) live in a separate, private repository. Its folder is `ORPHEUS_RESEARCH_DIR` (default `D:/Work/Research/Overwatch`). The tools read from it:

- `dumps/ingame_7FF788F10000.exe`: an image dump of the game in a match, rebased to `0x7FF788F10000`, the base the IDA list uses;
- `game/_retail_/Overwatch.debug.exe`: the decrypted game, prepared to run under a debugger;
- `docs/analysis/*.json`: hand-made names;
- `tools/dumpfix.py` and `tools/ida_apply_rose.py`: two research scripts that rebuilding the game database loads.

Other settings: `ORPHEUS_BIN` (the `orpheus.exe` the tools start), `ORPHEUS_GAME` (the install for `--game`; default `D:/Work/Research/Overwatch/game`), `OW_CODECS_JSON`, `IDADIR`, `ROSE_BIN`.

Game-data queries (`orpheus script query …`): the tools share one state folder, `research/out/orpheus_state` (`tools/paths.py` `ORPHEUS_STATE`). Its `cache/` holds the derived game data, seeded once from a copy of the user's cache; without one, the first query derives it in about 240 s, later queries take a few seconds. Pass both options after `script query`: `orpheus script query --state D:/Work/Coding/orpheus/research/out/orpheus_state --game D:/Work/Research/Overwatch/game <command>`. Never use the user's own state folder (`%APPDATA%/orpheus`). `show --full` prints field values whole (without it they are cut at 160 characters).

What the tools generate goes to `research/out/` (ignored by git). All paths are in `tools/paths.py`.

## The tools

- **`owindex/`**: an index of the client's runtime tables, built from the dump into `research/out/index/ow_index.sqlite` (`python -m tools.owindex.build`, about 10 s). `python -m tools.owindex.check` compares it with `crates/fixed/data/statescript_codecs.json`. It holds:
  - the 5,478 STU classes with their parents and fields (offset, type, network flags) and OWLib's labels. Labels only: the client keeps no names, and most classes and fields are just hashes;
  - the 1,735 statescript registrations (config 1027, state 438, action 260, entry 5, condition 4) with the winning one per class, its runtime vtable and its functions: config `evaluate` (slot 4), action `execute` (slot 10), condition `evaluate` (slot 8), state reader, block and writer;
  - all 1,216 network messages with their field layouts (the same as our schemas) and the client's handler, and the 127 entity components with factory, constructor, vtable, size and STU class (`net.py`);
  - names: `Eval_STU_x`, `Read_STU_x`, `Msg25005_Handler`, `Comp51_Ctor` and the names from the research;
  - the component type id stubs `CompId<N>` (`mov byte [rcx], N`): used by the component's factory and by its pool functions, which hand out the list of all N instances (component 114: `sub_7FF789C1A0A0`);
  - the starts of 21,114 function pointer tables in .rdata/.data (vtables): `python -m tools.owindex holds <function>` lists every table slot holding a function, with the slot, the table's name and what the index knows of it (STU runtime vtable and slot role, component vtable, message class, docs/analysis names such as ScriptHost_Vtbl). In Python: `.holders(rva)`.
  - the entity component accessors (`comp.py`): the 84 getters, tiny functions writing (mask, mask−1, shift, word) for the entity's component bitset at +0x88 (component = 64·word + shift), named `GetComp<N>`; `HasComp` (0x7FF78A73C470, `has(entity, n)` with n in edx) and the component of each of its call sites; every call site of both; each component's mirror (the networked STU instance its constructor builds in place) with its offset, so each mirror field has a component offset (component 74: mirror STU_6FF83459 at +0x70, field 6 m_CB549738 = +0xF6).

  Look up: `python -m tools.owindex CD7F3617 0x7FF789BE27C0 Eval_STU_CD7F3617`. A component: `python -m tools.owindex comp74` (data class, mirror fields with component offsets, getter, the functions using it); a class lookup says when the class is a component's data class or mirror. In Python: `from tools.owindex import Index; Index.open().stu(...)`, `.addr(...)`, `.messages()`, `.components()`, `.component(74)`, `.component_of_stu("8FE674F9")` (data class first, then mirror class), `.component_accessors()`, `.component_uses(74)`.
- **`ida_game/`**: an IDA database of the game, `research/out/ida_game/ow_game.i64`, built without the IDA window by `python -m tools.ida_game.build` (about 20 min; `--status`, `--phase P`, `--rebuild`, `--detach`, `--wait S` to wait for the database lock). It needs IDA 9.3 (`IDADIR`, default `D:\Program Files\IDA 9.3`) and Rose (`ROSE_BIN`). Phases:
  - `image`: checks the dump and deobfuscates about 6,300 candidate functions with Rose;
  - `create`: IDA's full analysis;
  - `rose`: puts Rose's results into the database;
  - `vslots`: makes a function at every slot of the index's runtime vtables, component and message vtables, factories, constructors and message handlers (about 16,000 targets; 4,700 were not functions: stubs between filler bytes, Rose-hidden code). About 40 Rose-obfuscated stubs stay undefined;
  - `names`: names from the index (including `GetComp<N>`) and the research (`docs/analysis/*.json`; the statescript value API `ScriptValue_*`, the statescript host `ScriptHost_*`, the protector's `Prot_DecryptKey`/`Prot_DecryptSlotIndex` are in `misc.json`);
  - `types`: a structure per STU class. Config evaluators and action runs get `STU_<H> *stu`; state readers and writers get `StateRt_<H> *this`.

  Several functions at once: `python -m tools.ida_game.decompile <address or name> [...] [--define] [--out F]` opens the database once and prints each function's pseudocode (disassembly when Hex-Rays fails). In Python: `from tools.ida_game import open_game_idb`, then `decompile(x, define=False)`, `define(x)`, `func`, `xrefs_to`, `callees`, `disasm`, `find_imm(value, width=None)` (instructions that use a constant: 4-byte encoding below 2^32, else `imm64`; bytes IDA has not made code are decoded too), `read(x, n)` and `qword(x)` on an RVA or an address in any known base. Each pseudocode line ends with `// @<address>`. `define=True` makes a function where none holds the address (from `.pdata`, else from the nearest referenced start that decodes to it) in memory only. One process at a time can open it, so open it for one batch of queries and close it (a held lock blocks every other agent); nothing is saved unless `save=True`.
- **`stu.py <class, address, name or ORPHEUS alias>`**: everything about one STU class:
  - its fields and what the network does with each;
  - the entity component it is the data class or mirror class of;
  - its registrations, and the inherited one the client uses. A class with no registration of its own has no client code: the client never runs it (server-only);
  - **every runtime-vtable slot** of that registration, marked `= base` or `DIFFERS` against the closest ancestor's registration of the same kind (STUStatescriptState, STUConfigVar, STUStatescriptAction; conditions are compared with the other condition registrations). Slot roles: known: reader 43 (+0x158), writer 42 (+0x150), block 45 (+0x168), type tag 1, evaluate/execute/run of handlers; inferred from the base state's code (`*`): begin 23 (+0xB8), end 24 (+0xC0), update 25 (+0xC8), after_begin 28 (+0xE0), event 18 (+0x90); slots 0–3 are per-class boilerplate;
  - the code of the named slots, of every slot that differs (`--slots all`: every slot), and of class-local helpers (functions that two or more of these slots call and nothing outside the class calls), as pseudocode from the game database (or disassembly), with the class's fields marked;
  - the functions they call;
  - where the game data uses the class (`orpheus script query`).

  Keys also accept the aliases and names in `crates/fixed/data/statescript_names.json` (`HeroSelect`, `ActionSendClientOnlyGameMessage`). Functions that several classes share are marked as shared, not given to the class. About 5 s without the database, 15–40 s with it.
- **`who_reads.py <class> <field> [--write]`**: the code that reads (or writes) one field, the strongest evidence first: a typed member access, a register known to hold the class, the field's hash as a constant, then matches by offset. Offset matches ("heuristic", "signature") are marked as guesses; data-only classes with fewer than 6 own fields get no signature scan unless `--signature N`. An asset reference field is 16 bytes in memory (an access at +8 is its GUID). It prints the `owdbg.watch` command that checks it in the game.

  **`who_reads.py --component N <+off | mirror field> [--write] [--size B]`**: the same for an entity component. Seeds: callers of `GetComp<N>`, the pool functions of `CompId<N>` and their callers. The component pointer is tracked through the slot lookup or the pool entries and their decryption, into functions that return the component or a member of it (and their callers, `--up`) and into callees that get it or a member address in an argument (`--depth`). "tracked (array element)": the field is in a mirror array of records and the access is the same offset in another record or indexed. "block copy" hits (16+ byte moves) are weak. Reads of encrypted pointer fields (xor with a 64-bit constant) are not hits. Not followed: pointers stored into other objects. About 2–30 s.
- **`owsearch/`**: searches over code and data that the index doesn't answer, in `research/out/owsearch/owsearch.sqlite` (`python -m tools.owsearch.build`, about 15 s, after the game IDB's `image` phase made `research/out/ida_game/ow_game.exe`; without it, it reads the dump).
  - `const <value|GUID|short id>`: the code using a constant. The build decodes every `.pdata` function of the Rose-patched image and keeps 16/32/64-bit immediates (as encoded: `mov r8, 0FFFFFFFFE1C1E402h` is `0xE1C1E402`), 4/8/16-byte loads from `.rdata` and direct calls. At query time it also scans code outside `.pdata` (Rose-hidden code) and `.rdata`/`.data` (tables keyed by a hash: the entry's next qword, when it is code, is shown). Each use: the instruction, its function with the index's name and description, and for unnamed functions their named callers and the data that points at them. `0x…` or 7+ hex digits is a value (a GUID-shaped one is searched as that GUID); `068A.025`, `000000000307.025`, `097:0001` a GUID; 1–6 digits without `0x` (`04AA`) a GUID index of any type. Values below 0x100 are not kept. `--json`, `--limit`.
  - `guid <value>`: type and index the way ORPHEUS writes them (`0307.025 game message (000000000307.025)`).
  - `cvar <hash|#index> | --all [--type T]`: the client's 1,601 console variables (registry `0x7FF78BD3B6B0`): type, value and default in the in-game dump, object address, and the code that reads, writes or takes the address of the object. The client keeps no names.
  - `read <address> [--qword|--dword|--float|--double|--string|--bytes N] [--count N]`: a typed read from the in-game dump, with the index's description and the console variable the address is in.

  In Python: `from tools.owsearch import consts, cvars, guid, connect`; `consts.search("0x1C6EC712")`, `cvars.lookup(connect(), 0x027006C2)`, `guid.describe(v)`.
- **`owdbg/`** (`python -m tools.owdbg.<command>`): a small Windows debugger. Every command starts `orpheus serve` on a temporary copy of the state folder and the game in a window under the debugger, loads the relay, clicks LOGIN after the client's usual first failure, and closes the game and the server at the end. Output goes to `research/out/owdbg/`. Never launch the game with `--tank_Console` or `--tank_ShowMode`: one of them opens a full-screen window that can't be hidden or closed.
  - `launch`: start and keep running (`--screenshot`; default `--duration` 600 s). Every command takes the machine-wide game lock for its whole session, so a session must end when its work is done: with `--actions` the session closes the game and the server `--close-after` seconds (default 5) after the script ends; `--keep-running` (with a long `--duration`) keeps it up, e.g. for a person to play.
  - `probe --at SITE`: log each call: arguments, memory (`[rcx+0x18]:8`), return value, caller, `--stack`, `--caller-in`. Site options (`--read`, `--ret-read`, `--caller-in`, `--no-ret`, `--max-hits`, `--max-events`, `--stack`, `--stack-args`) after an `--at` belong to that site; before any `--at` they apply to all. Calls owdbg makes itself (actions' set-view) are skipped.
  - `watch --addr X`, or `--arm-at SITE --field rcx+0xA8:8`: a hardware watch; lists the instructions and functions that read or write. `--this-vtable X` / `--arm-if 'EXPR=VALUE'` arm only on matching hits (a begin shared by many state types).
  - `watch` or `probe` with `--msg ID --field '#N' --send '{"#N": value}'`: the server sends message ID with that value (the `ORPHEUS_DEBUG_SEND` routes, [troubleshooting](../user/troubleshooting.md#marker-messages)). The watch starts at the client's handler and lists the code that reads the value. Game link messages need a match: `--enter-range --send-after-match` goes into the Practice Range by itself.
  - `cover run --phase NAME:SECONDS[:click=x,y]` and `cover diff`: one-time breakpoints on function starts (12,000 are fine); the functions first reached in each phase, and the difference between two runs.
  - `crash`: registers, the stack with names, disassembly and a minidump on an exception (`testdata/crashme.c` is a test program).
  - `--actions SCRIPT` (launch, probe, watch, cover; `tools/owdbg/actions.py`): an input script that runs once the match is entered. Steps: `wait`, `tap`/`hold`/`press`/`release BUTTON`, `fire`, `jump`, `crouch`, `melee`, `reload`, `interact`, `ultimate`, `ability 1|2`, `move DIR S`, `look`/`turn`, `aim-at-bot [N]`/`aim off`, `key N`, `screenshot`, `position`, `poke ADDR TYPE VALUE` (a memory write; an address inside the image is an ORPHEUS VA). A breakpoint in the client's input sampler (`0x7FF78961C7FC`) writes the buttons, movement and view into component 59's sample, so the client predicts it and the server receives it; no desktop input is used. Aiming calls the client's set-view; bot positions come from a background heap scan (about 15 s before the script starts). `--hero NAME` picks the hero at the first hero select; `--actions-start login` runs menu-time steps such as `poke`; `--foreground-input` uses SendInput and takes the desktop. Limit: `hero NAME` in a running match doesn't open hero select yet (`D:/Work/Coding/refs/reports/ClientInput.md`).
  - More `--actions` steps: `key CHORD` (`alt+\``, `enter`, `ctrl+shift+f`) and `type TEXT`, posted to the game window (no focus needed; SendInput with `--foreground-input`); `die`: the server kills our hero (`/api/debug/kill`, needs `ORPHEUS_DEBUG_SEND`, refused in the spawn room, so walk out first, e.g. `move forward 6`).

## owprobe: the in-process probe

`owprobe.dll` (`crates/probe`) runs inside the client and answers `tools/owprobe` on `127.0.0.1:PORT` (default 21150). Unlike owdbg nothing stops the game: a hook costs microseconds, not a debugger round trip, so the client keeps its frame rate (168 input samples a second with a hook on the rollback in the Practice Range, against owdbg's 3-20 FPS). Research and measurements: `D:/Work/Coding/refs/reports/ClientProbe.md`.

**Starting it.** `orpheus play --probe [PORT]` (also `host` and `join`; env `ORPHEUS_PROBE=PORT`) loads it after the relay into the first game. Its code hooks patch the client's code, which the shipped `Overwatch.exe` maps `SEC_NO_CHANGE` after its protector's remap, so give the decrypted debug build: `--game D:/Work/Research/Overwatch/game/_retail_/Overwatch.debug.exe` (the launcher takes an explicit `Overwatch.<name>.exe`). With the shipped exe only the memory commands work. owdbg sessions take `--probe [PORT]` too. `python -m tools.owprobe launch --enter-range --hero Soldier [--seed-state DIR] [--duration S]` does it all: `orpheus play --probe` (`ORPHEUS_BIN`, with `owwfd_relay.dll` and `owprobe.dll` next to it) with the debug build on a temporary copy of a state folder (`--seed-state`: where the derived game data and profiles are copied from, default `%APPDATA%/orpheus`, read only; a cache from another code version is derived again first, about 10 minutes), the login, TRAINING > PRACTICE RANGE, the hero and SELECT (about 60 s); it holds owdbg's machine-wide game lock. Run the other commands from a second shell. In Python: `with tools.owprobe.session.Session(enter_range=True, hero="Soldier") as s:` then `s.probe`.

**Commands** (`python -m tools.owprobe <command>`; in Python `from tools.owprobe import Probe`, methods of the same names). Addresses are ORPHEUS VAs (converted to this run's base), index or docs names (`GetComp4`), or `c59`, `ent`, `c4`:

- `info`, `modules`, `regions`, `read ADDR [LEN] [--type f32x3]`, `write ADDR HEX` (code too), `eval EXPR...`, `disasm ADDR`, `scan --value V` (heap words) or `--pattern "48 8B ?? 05"` (code), `components VTABLE|compN` (every component with that vtable and its owner's entity id, about 2.4 s).
- Read expressions (hooks, the sampler, `eval`): registers, `base`, `c59` (the local player's component 59), `ent` (the player entity), `c4` (our body's component 4), `[x]` (the pointer at x), `+`, `-`, and a type: `[rcx+0x18]:u32`, `[[rdi+8]+0x10]:f32x3`.
- `trace --seconds S [--out F] [--every N] [--read EXPR] [--input SCRIPT]`: the frame sampler. A hook at the input sample site (`0x7FF78961C7FC` in the sampler `0x7FF78961B350`, once per rendered frame on the main thread) records for each frame: the newest command frame of component 59's ring, our body's position (component 4 `+0x160`, about 1 m above the feet), a velocity (the position change over the time since it last changed: the position moves at the simulation's rate, not the render rate), the view (16-bit yaw and pitch), the buttons, throttles and action byte the sample carries, and the extra reads. JSONL into `research/out/owprobe/`.
- `input SCRIPT [--clear] [--wait]`: input written into the client's own input samples frame by frame, with the window in the background too (`tools/owprobe/script.py`): `walk 120` (input samples), `walk+jump 1`, `forward+right 2s`, `wait 500ms`, `look YAW PITCH`, `turn`, `free` (degrees, through the client's set-view `0x7FF7894E00A0`, so camera, prediction and command agree), `press`/`release BUTTON`, `key N` (a logical button's action code). Buttons: fire, fire2, interact, ability1, ability2, ultimate, jump, crouch, reload, melee.
- `hook ADDR [--read EXPR] [--ret] [--ret-read EXPR] [--stack N] [--set REG=V] [--max-hits N] [--mid] [--seconds S]`: an inline hook (a jump to a stub that saves every register, then the displaced instructions in a trampoline). Each hit logs the registers, xmm0-3, the caller, the reads and N callers unwound with the image's unwind data; `--ret` also the return (rax, xmm0); `--set` changes registers at the hit (an argument); `--mid` hooks a site inside a function. With `--seconds` it streams the hits into JSONL, prints the callers by count and removes the hook. `hooks`, `unhook ID`, `fetch`.
- `call ADDR ARGS... [--thread frame|probe] [--force]`: call a client function with up to 16 integer arguments (floats as their bit patterns, `f32_bits`), by default on the main thread at the next input sample. It refuses an address that is not a function start (the image's unwind data) unless `--force`. The call goes through a `call rax; jmp r12` gadget written into the image's padding, so the client's caller checks (the return address inside the code, a CALL before it) pass.
- `screenshot [--out F]`: the game window (owdbg's PrintWindow capture, window in the background is fine).
- Statescript, in Python (`tools/owprobe/statescript.py`): `hosts(p, entity_id)` (component 47 and its host at `+0xD0`), `instances(p, host)` (id, graph, GUID, flags), `states(p, instance)` (the state objects pointing at the instance: node index, vtable, flags; a heap scan).

Protocol: TCP; each message is a u32 little-endian length and UTF-8 JSON. Requests `{"id", "cmd", ...}`, answers `{"id", "ok": true, "result"}` or `{"id", "ok": false, "error"}`. The ring buffer keeps the newest 262,144 records; `fetch {since, kinds, hooks, wait_ms}` returns them in order with the next sequence number and how many were lost.

Pitfalls:
- The body: component 59's owner is the player entity (`A0000100`), not the body. The sampler takes the body to be the player's id + 1 (`A0000101`, the id the server's owner trace names) and finds its component 4 with a heap scan (about 2.4 s; again after a respawn or a hero change). `Probe.sampler(body=ID)` names another.
- `--ret` swaps the return address on the stack; an exception unwinding through the hooked function then finds no unwind data for the gadget. Use it on functions that return normally.
- A hook writes a 5-byte jump over whole instructions; a thread that returns into the middle of the displaced bytes (a `call` among them) skips the rest. Hook function entries or sites without a call in their first 5 bytes. An `int3` there (owdbg) is refused.
- A removed hook's stub stays in memory (a thread may still be in it); the ring drops its oldest records first (`lost` in `fetch`).

## Pitfalls

- **Index.** The client's STU classes form a tree (descriptor `+0x10` first child, `+0x18` next sibling, `+0x20` parent). The qword `0x7FF78B4F1640` at the start of a descriptor is the image's shared empty string, not a type marker; field entries and message records start with it too. Rebuilding the index while another process has it open fails, and the old index stays.
- Tiny functions (`ret`, `mov al,1; ret`, `mov eax,8; ret`) are shared by unrelated classes. A vtable slot that points to one says nothing about the class.
- In config and condition `evaluate` and action `execute`/`run`, the STU instance is in **r9**; `rcx` is the runtime object. A class's descriptor builder has every field hash as a constant (`mov r8d, <hash>`): that declares the field, it doesn't read it.
- **Messages.** Each protocol has two id switches; only the client dispatcher has handlers. A case that calls `0x1CCC660` (`xor eax,eax; ret`) is a message the client ignores (25016, 25017, all of 429xx). A handler gets the message in **r8** (`handler(rcx = handler object, rdx = context, r8 = message)`); owdbg checks it on each hit with the message's vtable.
- **Database.** Build it with `tools/ida_game/build.py`: research's IDA helpers expect IDA's analysis to be off and delete real functions in a fully analysed database. A killed build leaves `.id0`/`.id1` files; run `--rebuild`. Rose takes `-f` in batches of about 1,000 and runs without a console window.
- **Components.** An entity's components are a bitset at entity +0x88 and an array of encrypted pointers; code gets one through `GetComp<N>` (component = 64·word + shift) followed by an inline popcount and decryption, often inside a wrapper that returns the component (component 74: `sub_7FF789C1C210`). Components without a getter (e.g. 0, 11, 16, 19–23) are not searchable by `who_reads --component`. The mirror offset is measured from the constructor; mirror field offsets are relative to the mirror.
- **Statescript filters.** In config evaluators, `(*(ctx+0x10))->vtable[+0x150]` is `ScriptHost_EntityPassesFilter` (0x7FF789C1DA20): the object at context `+0x10` is the statescript host (component 47 has one at `+0xD0`). The filter's masks at `+0x20..+0x48` are tested by `Filter_TestTeamMasks` (0x7FF789ADAAE0): any/all/none team masks against component 25 `+0x58`, then include/require/exclude relationship bits 1 = not hostile or self, 2 = hostile, 4 = self. A state's vtable `+0x90` (slot 18) is `OnEvent(this, event)`; states call it themselves from other slots.
- **Decrypted globals.** Code that starts with `Prot_MaskingStub`, then `Prot_DecryptKey` (0x7FF7892338C0) and `Prot_DecryptSlotIndex` (0x7FF789239C60) decrypts a protected global pointer; which object it is shows only in the game (`owdbg.probe` after the call).
- **owsearch.** A list or map console variable keeps its items on the heap; the image dump doesn't have them. GUIDs that the code writes as two 32-bit halves aren't found. Outside `.pdata` functions only values ≥ 0x10000 are searched (by bytes).
- **owdbg.** It passes the game's own exceptions on (`C0000096`, `80000004` that isn't its own step, `C000001D`, `C0000005`, foreign `int3`), swallows `406D1388`, and calls a second-chance exception a crash. Debug registers are written 8 s after the start (`--hw-delay`; `0` for start-up). The game and the server run in kill-on-close jobs, because the game keeps its own handle to the debugger. A breakpoint costs about 0.1–0.3 ms; use `--max-hits` on busy functions.
- The client's first login attempt always fails; owdbg clicks LOGIN until the relay connects (25–82 s). Now and then the relay hooks the wrong stream first and that run can't log in; run it again. A body without HUD and weapon after a spawn was the stale initial owner frame, fixed 2026-11-17 (behavior.md); if it shows again, run the server with `RUST_LOG=info,orpheus::owner=debug,orpheus::join=debug` (creates, possession, controller and owner frames as sent and acknowledged) and probe `0x7FF78991E050` (a return of 2 is a skipped owner frame).
- A field watch sees only reads of the message itself. Handlers often copy a field into a local first: use `--linger`, or watch the copy.
- **Actions.** Reading the game's memory on the debug thread stalls the game long enough to drop its link to the server: scan on a worker thread, as `actions.py` does. A button press is one sample: holding a toggle button over several command frames sends several press/release pairs.
