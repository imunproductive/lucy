# Data sources

What the server reads, where each input comes from, and the facts needed to rebuild it from the game install. Saved from the inherited documentation and tool comments.

## Runtime files

The server derives its game data from the install (`crates/assets`, see [architecture](architecture.md#data-flow)) into `<state>/cache/104319`, in the format of the prepared runtime pack the inherited server read, so the loaders read it unchanged. A stamp file (`derived.txt`) records the build, build config, locale and derivations version; a cache with another stamp is derived again. The prepared pack stays as the oracle each derivation is checked against (`just test-assets`, `lucy assets diff --pack`). The fixed data is embedded in the binary (`crates/fixed`).

## Asset formats

- **ENTITY map chunk** (type `0x0B`, as TankLib's `teMapChunk` reads it): header `{u32 placeable count, u32 instance data offset, u32 placeable offset, u32}`. Each placeable has a 24-byte header `{uuid, u16, u8, u8 type, u32 size}` and a body `{u64 definition, u64 identifier 1, u64 identifier 2, f32 translation[3], scale[3], rotation[4], u32 instance count, …}`. From body `+112`, one `{u32 type, u32 offset}` per instance, each an STUv2 blob (`"DUTS"`, u32 version, u32 instance offset).
- **AI spawner** instance `STUECAISpawnerInstanceData` (`0x99257985`): `+8` the hero (`075` asset reference, GUID in the second half), `+24` an identifier (`01C`; 0 means every mode). Hint instance hash `0xF199249B`.
- **Navigation map chunk** (kind `0x12`, `0x0DD0 << 48 | 0x12 << 32 | map index`, all 132 maps): header `{u64 document 0 offset, u64 document 1 offset, u64 record count, u64 record offset}`, the records 64 bytes each (an identity-like matrix, not read). 54 maps have no documents (both offsets 0); map `06C7` has documents but no volumes. The documents are STUv1 (`"DUTS"`, u32 instance count, `{i32 offset, u32}` per instance), fields at fixed offsets in the type table's order, arrays 16 bytes `{i32 offset, …}` pointing at `{i64 count, i64 first}`.
  - Document 1, root `STU_5AE64839`: `+0x08 m_dynamicTreeDef` (inline: `m_aNodes`, 64-byte AABB tree nodes `{f32 min[4], max[4], u64 volume, i32 parent, child 1, child 2, height}`; `+0x18` node count, `+0x1C` root, `+0x20` proxy count = volume count), `+0x28 m_volumes`, `+0x38 m_chokes` (empty on every map), `+0x48 m_B1E00012` (one int), `+0x58 m_metaData` (embedded `STU_A74C30E0` markers: `m_52EA7AB9` position, then data the type table doesn't name), `+0x68 m_276CC7EC`. A volume (`STUAITacticalVolume`, 0x68 bytes): `+0x00 m_42286A80` walkable mask words, `+0x10 m_63EE0EDB` the walkable cells with a same-layer 8-neighbour outside the mask (the border; 117 of 117 on Temple of Anubis), `+0x20` neighbour indices (s32), `+0x30` floor point, `+0x3C` five floats and `+0x50 m_FEF6FAAD` (not understood), `+0x54 m_id` (its index), `+0x58` origin (s16 x, layer, z) and size (s16 Sx, Sy, Sz). Tree leaves bound their volume from origin to origin + size. On all 77 maps every floor point lies in a walkable cell of its volume, with the layer `round(y / 0.35) / 4` (floors sit on the 0.35 m grid, a float error either way; `floor(y / 1.4)` misses 3 of Temple of Anubis's 117, which may be why `docs/notes/ow1-preservation.md` reports partial fits), and every link is symmetric. Temple of Anubis: 117 volumes, 113 links, a main group of 85; Practice Range: 67 volumes, 62 links.
  - Document 0, root `STU_3BC32A6E` (AI cell data): `+0x08 m_cellData` (`{u64 key, u64 hash, u32 index into m_cellBytes}`, the key `(y + 0x80) << 24 | (z + 0x800) << 12 | (x + 0x800)` of the client's grid of 16 × 22.390625 × 16 m cells), `+0x18 m_cellBytes` (one byte block per cell; keys with the same hash share one), `+0x28 m_collisionCrc`, `+0x30 m_D4E3DEAB`. A block holds two voxel graphs, the walk layer above floors and the free air, each a tree of 4 m bricks, 1 × 1.4 × 1 m units and 0.25 × 0.35 × 0.25 m voxels with links between units; the layout is in `lucy_physics::ai_cells` and `D:/Work/Coding/refs/reports/Navigation.md` ("DayAiCells"). The client's path query (`0x7FF78A626BC0`) searches the air graph in mode 1 and the walk graph in mode 0.
- **Map placeables:** the client gives map placeables one flat index over the placeable types whose flag is set in its type table (light, area, entity, … in that order), so the first entity's index is `count(light) + count(area)`. Placeable type is byte 19 of each placeable: light 7, area 8, entity 9. Spawn component bit 58 (`0x737C5C41`), required component bit 94 (`0xCA1FB0B8`).
- **CASC (local install):** the local index `data\casc\data\XX*.idx`. Bucket XX is the first 9 bytes of the encoding key XORed together and folded to 4 bits; the newest version of each bucket wins. Entries are 18 bytes: 9 bytes of key, 5 bytes big-endian `archive << 30 | offset`, u32 size. In `data.NNN` at that offset sits a 30-byte header (the key reversed, u32 size, …) followed by the BLTE file: `'BLTE'`, u32 header size, then blocks stored (`N`) or zlib (`Z`). The content key is the file's MD5. An asset inside a bundle has its own content key and size, plus the bundle's keys, size and the asset's offset.
- **CASC GUID lookup (`crates/casc`):** `.build.info` (active row) names the build config and keyring under `data\casc\config\ab\cd\<hash>`. The build config names the encoding table (by encoding key) and the root file (by content key). The root file lists the `RDEV` content manifests (`.cmf`): one base, plus text and speech per locale. A 104319 CMF header is twelve u32s ending in asset count, entry count and magic; the body is AES-256-CBC encrypted with TACTLib's `ProCMF_104319` key and an IV from the SHA-1 of the manifest's file name. Assets are 29 bytes `{GUID, u32 size, u8, content key}`. Bundles (`09C`) start `{i32 count, u8 offset size}` with `{GUID, offset}` entries; the asset size comes from the manifest. Encrypted BLTE blocks (`E`) are Salsa20 with a keyring key; the IV's low 32 bits are xored with the block number.
- **Structured data (`crates/stu`):** an STUv2 asset starts with three `{i32 count, i32 offset}` tables (instances `{class hash, field hash, instance, size}`, inline array types, field bags of `{field hash, size}`), then the size and offset of the dynamic buffer and the offset of the data buffer. Each instance in the data buffer is a field bag index and that bag's fields; a size of 0 means the field's size precedes it. Arrays, strings and hash maps live in the dynamic buffer. Asset references are stored xored with the field hash (repeated in both halves) and the CRC-64 of the 36-byte header (reflected polynomial `0x95AC9329AC4BC9B5`, zero start, inverted output), with bytes 0/3, 7/1, 2/6 and 4/5 swapped. Fields an asset doesn't store take the class's declared default.
- **The key the install lacks:** 8 bundles are encrypted with key `28B8EBB462B83EEA`, which the install's keyring lacks (OWLib's support keyring labels it "[1.74] ???"). They hold 1 of 1,587 graphs (`1D6D`), 19 of 3,528 definitions, maps `0EEE` and `0F14`, the Genji "Happi" OWL skin (`000000005058.0A5`), and some models and strings. Those two maps are main menu lobby maps, "OWL Summer Showdown 2022" and "Goodbye" ([Logo2K's lobby map list](https://rentry.co/wcwyv3r8)). TACTLib's static `Overwatch.keyring` has the key (tagged `[1.74]`), and DataTool uses it too, so the recorded export has those assets; `crates/casc` uses it when the install's keyring lacks it, and every graph and definition reads and matches its content key (`just test-game`). The derived lists need it for the Happi skin; nothing derived references `1D6D`.
- **Message schemas in client memory** (how `lobby_schemas.json` and `game_schemas.json` were dumped from a running 1.74 client, read-only): the client keeps one `JamMessageInfo` per message `{name*, protocol*, items*, u32 crc, u32 message_id}`. Items are 0x30-byte records `{name*, u32 type, u32 offset, u32 size, i32 count, inner*, resize*, bits}`; type 17 ends a list, type 14 nests a struct through `inner*`, and a non-null `resize*` marks an array. The game link's protocols have no announcement: they sit in a fixed table in the client's message system (0x7FF789B797C0), in wire-index order.

## Where a runtime pack comes from

The upstream ORPHEUS repository never committed the pack's files: its `data/` held only `README.md` and replays in all 204 commits, and `prepare_server_runtime` only copies files from a private "prepared checkout". The pack now holds only game data, which phase 6 moves to CASC; the fixed data is embedded. LizRollin's repository commits all of its files in `data/`, except the collision caches. The collision caches: `tools/build_collision.py <map>` with `LUCY_RUNTIME_DIR` set to the pack builds them from the install. `0688.col` built this way matches the recorded SHA-256 below. The Python tools named in this note were deleted in phase 8; the commit tagged `python-reference` still has them.

The pack has two graph bundles, both made by `tools/extract_game_graphs.py` from DataTool XML dumps of the install:
- `game_graphs_174.json.gz`, the hero bundle the server runs: 373 graphs, 32 bodies, `0F9C` missing. `--xml <dump> --owlib <OWLib>` alone gives exactly LizRollin's file. The pack's copy also has the 25 modes' variables (`--mode-xml <dump>/0C5`) and each body's authored target tags (added by the former `lucy runtime prepare --target-tags-xml <dump>/003`; the derivation now reads them from the install), as upstream's had: without them the Soldier: 76 VM stops earlier (see `docs/notes/behavior.md`). SHA-256 `a1d42e17781904d9a209c432f1655f3504e30c93e3f303a799ec2509dc092431`.
- `game_graphs_bots_174.json.gz`, for VM tests of the bot graphs (`testkit::bot_graphs`): 405 graphs, 8 entity definitions, 25 modes' variables. The same plus `--ai-spawners <pack>/data/ai_spawners_174.json --mode-xml <dump>/0C5 --entity 1403 --entity 143E --entity 146E --entity 14A9 --entity 14D2 --entity 14ED --entity 1404 --entity 14AF` (the six Practice Range bot bodies and the AI definitions their `m_8B9A461F` names). It holds the Practice Range bot graph `0B92`. SHA-256 of the built file: `6821d7a3c53d4efd12a26959164c39545b781604ea4407feb4ac57432f86d990`. Its digest matches the Python reference vector for the 405-graph bundle. The server can't use it yet: with bot graphs the Practice Range scene is not movement-ready.

The dumps: OWLib at the pinned revision, built with the .NET 8 SDK (a `global.json` pinning `8.0.418`; SDK 10's C# 14 breaks TACTLib's `Reverse()` calls) and run with `DOTNET_ROLL_FORWARD=Major`: `dotnet DataTool.dll --language=enUS --speech-language=enUS <install> extract-stu-type <dump> <type> --xml` for `01B`, `003` and `0C5`. It reads 1,587 `01B` and 3,528 `003` files from this install, offline.

## Collision caches

- Practice Range `0688.col`: format 5, 470,397 bytes, SHA-256 `dfdb71fbe9ad079d9d0b56fe12bd7c992a76c6ec942084d86f6388827f36a169`.
- All 95 catalog maps have integrity-checked format-5 caches. Workshop Green Screen uses a checked slice of its CASC bundle; both the container and the asset content keys are verified.
