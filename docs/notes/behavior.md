# Behavior and acceptance

What the server must do, what has been seen with the original client, and the known defects. Saved from the inherited documentation. New client acceptance results are added at the end.

## Acceptance targets

The first acceptance group is Soldier: 76 and the training bots in the Practice Range. Doomfist is the next hero.

| Milestone | Exit criteria |
| --- | --- |
| M0 Research and replay | Reproduce a known baseline with shared entity, time, input, event and state contracts. Track unsupported protocol and graph behavior. |
| M1 Body and weapon | Soldier: 76 keeps the expected model, weapon and ammo HUD for 60 seconds, with ten switch-and-return cycles and ten exits and rejoins. |
| M2 Rifle and prediction | Hold and release fire, empty the magazine and reload repeatedly. Client ammo and effects agree with the server, also with lost and repeated input. |
| M3 Single-player combat | Repeatedly hit, miss, kill and reset a training target. Its visible health, identity and combat feedback agree with the server. |
| M4 Movement and two clients | Two clients agree on movement, line of sight, combat and respawn. Loss, delay and reordering recover without extra damage. |
| M5 Match rules and heroes | Complete a full match in one mode on one map and return to the lobby. Each supported hero's declared abilities work. |
| M6 Fidelity and reliability | Timing and behavior compared against references. Long sessions, recovery, performance and repeatable deployment verified. |

### What the Rust server does

- Runs the local Battle.net listener, the encrypted lobby and the UDP match worker on loopback.
- **Lobby, Battle.net and dashboard connections** (2026-11-22, server change, LobbyConns; unit tests in `wire::tcp`, `bnet::service`, `dashboard/http.rs`, `lobby/hub.rs`, game-install tests in `lobby/tests.rs`; research `D:/Work/Coding/refs/reports/LobbyKeepalive.md`). Each connection has a thread that ends and is joined when the connection ends; stopping the server closes every listener and joins every thread (`architecture.md`, "TCP connections"). No byte on the wire changed.
  - **The client's lobby keepalive.** Once its link is negotiated, the game sends a heartbeat (control frame `00 03`) every 5 s (console variable `0xC5BEA490`, 5000 ms, in the client's gateway timer `sub_7FF7894709C0`; seen live: 22 in 112 s), and the lobby answers each. The lobby sends its own (`PONG`) after 10 s without one. The client's own reaction to a silent server after 20 s (`0xABD1A867`) is an event to its listeners whose effect was not traced.
  - **Lobby (3724)**: at most 32 connections, 8 from one address (a household behind one public address, or the games on this PC; each game holds one, plus a short BattleTag query from a joining launcher). The handshake (or the BattleTag query) must end within 30 s of the accept and the login message arrive within 30 s of the handshake (`ow174` used 30 s too), on the lobby's clock. - **Input timing** (2026-11-13, new behaviour; Python ran each command when it arrived; retail's rule from the GDC 2017 netcode talk, refs/reports/GDC-Netcode.md §1). Each tick runs one command of each player, the next in frame order, from a small buffer (`replication.rs` `InputQueue`), just before the tick simulates and sends (`RoomLoop::pass`). Frames already run or admitted are dropped (the client's redundant window resends them), later ones wait. The target is one command in hand besides the one a tick runs (retail's "one buffered command" for a steady stream): a datagram up to a tick late still runs on time. The first command waits a tick to get there, so a command runs one tick (16 ms) after it arrives: the latency this costs. At most 4 wait; a longer buffer runs its oldest at once. Retail's client grew and shrank the buffer by dilating its frame (16 to 15.2 ms, one command in 20 frames), told by the server. Since 2026-11-18 the server tells ours the same way: every world frame's ch3 clock flags (`lucy_wire::entity` `CLOCK_*`; the client's clock step 0x7FF789D28B10 scales its frame time by 1 ± k, k = 0.00625 in the 1.74 client, with flag 8 by 1 ± 4k again). Since 2026-11-22 (LatencyFix) they follow the client's lead, as retail's server measured "how early or late each command frame arrives": each command frame, the first time it comes, against the server's last tick; the latest of them since the last tick decides (`replication.rs` `clock_flags`). 2 frames ahead (the next tick's command and one more in hand before it runs) asks for nothing, 1 for a faster clock, 0 or less four times as much; 3 for a slower one, 4 or more four times as much; a resend or a dry tick keeps the flags. From 2026-11-18 to 2026-11-22 they followed the buffer's depth as a tick took its own, which the trimming to 4 and the waits kept at 1-4 whatever the lead: a client 11 frames ahead after a spawn got "slower" or nothing and came back by 0.2 frames a second, while every dry tick after a stall asked for four times as fast (refs/reports/Latency.md §6, "Stage 2"). The client's clock jumps ahead on its own at each spawn, to the newest packet frame plus its link round trip in frames (up to 16), which right after the map loads still holds the loading's stalls. Before 2026-11-18, we sent 0, the client never adjusted its lead, and under the debugger the buffer ran dry about 500 times a minute; every dry tick that stood in for a press moved the server's volley one to four frames after the client's, and the client's rollback to that frame drew the Soldier: 76 ammo counter as 0, then 30, on each tap (refs/reports/OwnerPrediction.md, 2026-11-18). With the flags, after the first minute of a game a few dry ticks a minute remain and the six presses of a run started on the client's frames. The server still does it from its side too (assumption): more than one waiting for 20 ticks in a row runs one more; one or none in hand while the client sends waits a tick. A tick with no command (a dry tick) first waits for the client's next frame, up to 4 ticks in a row (`MAX_WAIT`, 64 ms: retail's buffer before mid-2016; a lost datagram's commands come with the next, which carries every command since ack − 1): the frame then runs with its own buttons, click and action, as the client predicted it (2026-11-19). A longer silence repeats the client's newest input for the next frame each tick (movement keys, aim and held buttons, no click or action), as retail's server did (Ford 30:50: retail duplicated the last input to bridge the gap until the client, told to run faster, refilled the buffer; he gives no count), for at most 28 frames since his last datagram with commands, so the wait and the repeats hold his input 0.5 s (`MAX_REPEATS` = `HOLD_INPUT_FRAMES` − `MAX_WAIT`, the mover's own horizon for a held input; 2026-11-22, MapAnim.ConsoleSlide). Before, 4 frames: a stalling client (game sessions on a loaded PC) goes silent for 150-450 ms with his keys held, then sends every frame late, and the 4 repeats stopped his body while his client walked on, which his client was then corrected for (refs report MapEntities.md "Console slide divergence (MapAnim)"). Later dry ticks each run a neutral frame: his aim, no button, no movement key. So a silent body still simulates for the others (it falls, lands, its timers run) but stops walking, jumping and firing half a second after his last datagram (2026-11-19, DayLatePress: with no cap a silent test client's Soldier: 76 kept firing until he killed a wounded teammate). The ack stays at the client's newest command, so the client still sends the frames the repeats and neutral frames stood in for, and when they come a press or release those frames missed runs with the next command: a button they held through a release is up for that frame, one they never pressed is down (with its click); a button the client held through a neutral run is pressed again by his next command. - **One thread per match** (2026-11-22, server change, RoomThreads; game service tests `rooms::a_silent_game_leaves_its_match_and_the_closed_match_answers_nothing`, `rooms::two_matches_run_side_by_side_on_their_threads`, `rooms::a_match_that_panics_sends_its_game_home_and_the_other_plays_on` (gametest only) and the slow match tests; not checked in the game). Each match runs on a thread of its own with its own loop and clock, and one router thread owns the UDP port (3730) and hands each datagram to its match by the connection id in its header (`docs/dev/architecture.md`, "Game service and simulation"). A match slower than its ticks no longer holds up the others. Every match ticks on one 16 ms grid from the server's start, so a moment has the same frame number in every match, as when one thread ran them all. Timeouts and limits:
  - A reserved seat whose game doesn't connect within 60 s is freed (`HANDOFF_TIME`); a connected game that sends nothing for more than 10 s leaves its match (`SILENCE_TIME`), which the lobby sees as its seat going; after 20304 a game has 3 s to close its link (`LEAVE_GRACE`). As before, now kept by each match.
  - The router drops a datagram for a connection no match has (its match ended, its link closed or timed out) and one that can't be a game's (shorter than the link header, without its magic byte, longer than 1264 bytes), before any decryption.
  - At most 64 datagrams of one game wait for its match (about a second of them, `router.rs` `PEER_DATAGRAMS`); the router drops more, so a game that floods can't crowd out the others' input.
  - At most 256 of a game's reliable messages wait for a lost one before them (`ingress.rs` `MAX_PARKED`); past that the game is broken: it gets 20304 and leaves. Its commands were already bounded: at most 256 wait (`replication.rs` `MAX_PENDING_INPUT`, past which it leaves) and none more than 96 frames ahead.
  - A match whose loop panics ends alone, in a build that unwinds (release, gametest; the debug build aborts the whole process): at its next tick its games get 20304 as at the end of the clock's frame range, the players whose games haven't connected leave at once (such a game gets only 20304 if it still connects), and its seats go as its games close their links or time out. If it fails again meanwhile, it ends at once and its games time out on their own.
  - A match ends with its last player. It stays only while a game taken out before it connected may still connect (up to 60 s), to send that game its 20304.
