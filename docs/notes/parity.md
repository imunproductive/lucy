# Python and Rust parity

The frozen Python server (`ow174/`) is the behavioral reference until the Rust server covers what it does. This note lists the gap and the cutover criteria. Phase 8 of the [refactor plan](../REFACTOR.md) fills in the test inventory and then deletes this file.

## What the Rust server does today

- Runs the local Battle.net listener, the encrypted lobby and the UDP match worker on loopback.
- Login subset: presence, progression, the hero collection, the dated Arcade roster, priority passes, career mode rules, celebration content, party and ranked messages. Gallery equip, also while hero selection is open; a skin change of the active hero replaces the body.
- Selects a profile from `--account`, `default_account.txt`, the first saved profile, or the local template, in that order.
- Serves the solo base Practice Range. A headless test logs in over the encrypted lobby, requests a solo seat and uses the returned keys to authenticate UDP and receive the map load.
- Player movement on prepared collision: ordered per-body contacts and the same pose and wire quantization as the reference. Input work is round-robin, up to 16 poses or events per peer and 64 per event-loop turn. A 96-frame lead limit and a bounded input queue protect the worker. A correction history selects the eligible pose; sending owner corrections still needs authored hero movement parity.
- Statescript: expression evaluation (map building, angle and trigonometry opcodes, random floats), startup and same-time actions, scoped message entries, static and re-evaluated waits, server-frame waits, the deferred update phase (`Defer`), logical button edges and buffering, button blocks (`DisableLogicalButton`), AI weapon buttons (`AIFireWeapon`), variable stacks and keyed map writes, part of ability activation and `StopAbility`, `CycleIndex`, client-only pulsers and the kill feed pulse gate (`ProjectedSnapshot::gate_kill_feed`), `MoveTo` requests, owner and observer full and cumulative frames, authored target tags, health pools in `Vitals`, delayed conditional states, the operand-free instance exit. Every hero's and mode's ruleset defaults (`orpheus_script::rulesets`). The crate also has, for the sim to wire up: the ultimate charge (`ultimate::UltimateCharge`) and game messages between bodies (`PlayerWorld::take_messages`, `Component::receive_message`).
- Soldier: 76 rifle, reload and Helix cooldown run in reference tests. A fixture weapon damages a bot, retries a dropped hit, updates its health and respawns the bot over encrypted loopback. Helix flight and splash use the shared health path with a fixture body.
- The Practice Range training bots run their body scripts (`bot_script.rs`; match.py `_prepare_bot_script`, `_pending_bot_scripts`, combat.py `_bot_weapons`, `_bot_died`, `_advance_bot_death`, `_respawn_bot`): one script starts per update and the world waits for them; each client gets every bot's H=0 frames once its create arrived, the practice nameplate (0D24) once the mode UI arrived, the firing bots' live frames, the death script's frames with the kill feed pulse gated, and the respawned bot's new script. The three firing bots (0B92) fire their rockets along their yaw at the players and the other team's bots.
- Several players in one Practice Range world (`GameService::open_prepared`, and `open_practice_party` for a group of up to six on one team; the lobby does not open one yet). Each client gets the other players as `ow174/game/match.py` sends them: their 20308 cards (sent once more after 2 s, "joined the game" for a later arrival, "left the game" when they leave), controller entities, 288D team list entries, possession (44/75) once entity and body arrived, body creates, a movement record of each other body in every send frame, their body statescript as H=0 full frames and deltas (`observers.py`), and the destroys on a hero switch or a leave. A two-client loopback test checks the order. The 0C90 hero switch line is built for the PvP modes, which have no world yet.

## Still Python-only or open

- The stock Soldier: 76 owner script runs on the server path (checked 2026-11-10 without the client): a scripted session (fire through a reload, move, sprint, crouch, Helix, melee) runs with no gaps and every frame encodes for the owner and observers (`stock_soldier_plays_a_scripted_session`). Where the server can't do what the graphs ask yet, it does what the Python reference did. The VM records each such answer in `Snapshot::assumptions`, and the session test lists all 13 it reaches:
  - no-op actions: the unnamed `STU_E9694EFD` (sprint), `STU_6E5C5F66` and `STU_1C2CC6D5` (melee). Python's reasoned server no-ops (effects, criteria, stats, client-only messages, `PlayScript`, `STU_7106C356`, `STU_C43F9944`) aren't recorded: they change nothing the server tracks;
  - `STU_ED45C5E8` (graph `01CA`, node 126, server-only; moving and firing reach it) answers no entities, so message `0BD` goes nowhere; a message to nobody doesn't read its parameters;
  - an animation without a length in its graph (graph `02C5`, node 51) doesn't end by itself. Its length is that of the animation an alias (`0C8`) resolves to, but an alias asset holds no data (`STUAnimAlias` has no fields): the alias is resolved elsewhere, through the animation blend trees or client code, so reading assets alone may not give the length;
  - target searches (`TrackTargets`) find nothing; melee's health change, knockback, hit list and three unnamed states are on/off only, so melee hits nothing;
  - a map value (graph `05AD`, variable 29859) is left out of frames: its wire form isn't known, and the client builds the same map.
  The stock body turns on owner corrections (`replication.rs`). None of this has been checked with the client yet.
- Other heroes' owner scripts (checked 2026-11-10 without the client, by starting each body through `PlayerBodyFactory` in a debug build). Reaper, Pharah, Cassidy and Soldier: 76 start without a gap; `scene_assets.rs` runs only Soldier: 76. Every ruleset default now comes from the table, so Tracer's pistols load 40 rounds (`tracer_pistols_load_forty_rounds_from_the_ruleset_defaults`). A body with any startup gap gives no shots (`take_shots` waits for a complete start), so one unsupported node in an ability graph also disarms the gun. What still stops the others in debug builds is all graph content the Python reference didn't model either, so release builds run it the reference's way (see Statescript below):
  - config values Python answered null: `STU_E72F6348` (12 heroes), `STU_9B213168` (7), `STU_D3685C04` (5), `STU_71A87E92` (5), `STU_9B7648C3`, `STU_ED807E07`, `STU_038C32E8`, `STU_967463AB`, `STU_06610EBC`, `STU_60146072`, `STU_082FA44E` and a few single ones; forms of `STU_783B4CF0`, `STU_32E6E4D8` and `STU_AC829876` the evaluator doesn't compute;

  - one action: `STU_064A9E0D` (Bastion).
  Tracer's other gaps: Blink's action `STU_A807207A` (the move itself, with parameters 0.1 and 1); Recall's container `STU_54FEB21C` (node 4), which ends only when instance variable 395 (`0x018B`) turns true, as ow1-preservation found; nothing writes it, so the server must. Outside the VM: Blink and Recall move the player, so the mover must apply them (ow1-preservation did both as server teleports, Recall from 3 s of position history); the pistols' muzzle variables `0x31`/`0x32` stay empty, so shots would start at the body; Pulse Bomb's projectile `0x0400000000000045` sticks and explodes (graph `0C1B`), which the projectile flight doesn't model.
The rest, from a module-by-module comparison of `ow174/` with the crates (2026-11-10). "Builder only" means Rust can encode the message but nothing on a live path sends it.

- **Statescript.** Python runs every hero's body script and the bots' scripts; Rust runs both. The bots' come from the bot bundle (`game_graphs_bots_174.json.gz`), and the stock ones reach content the VM doesn't know (`STU_F76C486C` in graph 0033), so debug builds and tests start them only with `SceneAssets::set_bot_unknowns(Unknowns::Tolerate)`. Python treats an unknown state as a plain state, an unknown action as "follow the out plug" and an unknown native as null. Rust does the same in release builds and records each case as an assumption, logged once per server run; debug builds and tests refuse the body instead (`vm::Unknowns`). The node classes, opcodes and configs Python modelled are all in the VM now; Raycast follows its out plug without casting, as the live Python server had no cast provider. The sim runs the ultimate charge (#342 over 60 s, paused while the ultimate runs), the kill feed pulse gate for owner and observer frames, game messages between players' bodies and `MoveTo` requests on the mover. Assumptions the new code records: `WaitForServerFrames` takes a server frame as a 16 ms command frame, and `STU_4E2BCAAB` answers false.
- **Match.** Only the Practice Range has a world; several players share it and see each other (bodies, cards, team list, possession, observer frames, join, leave and hero switch notices), shoot and melee each other and the bots, die (25004, 25005, the 003E kill feed line, the dead flag in their movement records) and respawn after the mode's time as a new body; the Tab board, ultimate charge and spawn voice lines are live. Missing: other maps and modes (`MapCatalog::game_map` is test-only); joining a running match (`join_match`, `open_matches`, `lineup`); the Biotic Field's entities and heals (03DC, graph 0258: the building blocks and the canister's schedule exist in `projectiles.rs` and `projectile_wire.rs`, and `Combat::heal_area` / `heal_players` heal, but the match doesn't create the field entities or pass the heals yet); projectiles shown to other clients, the firing bots' rockets included (`ObservedProjectile` exists, not wired; projectiles.py 349-361, server.py `retain_bot_volley`); the PvP assemble countdown.
- **Lobby.** After login the Rust lobby answers every message Python's does. Missing:
  - matchmaking: queue matches open only on the Practice Range scene and only for one player, and a party can't enter the Practice Range together yet (the game service can open a world for several players, `open_prepared` / `open_practice_party`, but the matchmaker doesn't call it yet, and it can't add players to a running match or open other maps); the PvP assemble countdown, so a match counts as waiting for its players for its whole life; the party state's role queue fields (20700 +0x18, member +0xC8) are not filled in.
- **Dashboard.** `game_instances` stays empty: the game service reports no per-player hero or state.
- **Platform.** `--game-port 0` gives a random port instead of turning the game server off (the lobby needs it); no `--test-players` (there is no matchmaker), `--save` or research `inject.jsonl` watcher; the start banner has no schema count; a taken port is a plain OS error. The multi-PC modes (`host`, `server`, `join`, `join-tournament`) and the second game on one PC work on loopback but are not yet verified with a second PC or a second real client.
- **Game data.** Every runtime file still comes from the Python extractors (`tools/extract_*.py`, `build_collision.py`); `orpheus runtime prepare` only copies them, and Rust can't build a missing collision cache. `crates/casc` and `crates/stu` are not used by the server yet (phase 6c, 6d).
- **Open verification items:** on-fire scoring and decay, the tips registry, network serialization of map values, instance overrides and foreign entities for target tags, named pools and pool resize rules, the randomized timer's client parity.

## Cutover criteria

| Area | Exit criteria |
| --- | --- |
| Transport | Rust reproduces the reference bytes and fragmented streams, rejects malformed records, and handles loss, duplicates and rollover. |
| Login and lobby | The reference service requests and replies match. Existing profiles and runtime formats load. A lobby client acquires a valid match seat. |
| Match simulation | Registered state and packet order match encrypted Practice Range and two-peer replays. Sustained-fire tick time and snapshot gaps are measured with the same inputs. |
| Tools and dashboard | Replaced as described in the refactor plan (phases 4, 6 and 7). |
| Deployment | The launcher and relay work from a source build with the original client. |
| Cutover | Broader verified coverage than Python, the replacement workflows verified with the original client, and a server-only smoke test. |

When comparing the two implementations, use the same clock, input, collision data and packet-loss schedule. Compare bytes where the format is fixed, and decoded event order and registered state where runs contain nondeterministic values. Measure tick latency and snapshot gaps before claiming a performance improvement.
